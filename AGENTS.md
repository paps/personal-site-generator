# personal-site-generator

This public repo contains my personal site generators, i.e. my personal site can be generated by the generator that I choose. Each personal site generator is a Static Site Generator (SSG) (much like Hugo or Jekyll, but custom built), uses Node and TypeScript, and is fully isolated in its own directory at the root of the repo. From now on, we'll call those a "SSG", plural "SSGs".

The goal of a SSG is to correctly transform `.md` files to `.html` files from the source data repository (more on that later), where the produced HTML is nice to look at, the pages are clear and legible, the whole site easy to navigate, while preserving all the other files (non markdown files) in their original state to be served as-is, including being linked to from the md/html files.

SSGs have to be isolated in their respective directories at the root of the repo in form `<YEAR>-<MONTH>-<MODEL>` where `<YEAR>`, `<MONTH>` represent the date at which the SSG was created (lowercase full-length English for the month), and `<MODEL>` represent the AI model that created it. For example, `2026-january-gpt53` is a valid name. From now on, such a directory will be referred to as `<ISOLATED_SSG_DIR>`.

## Creating/modifying SSGs

If you're working on creating a SSG and the corresponding directory already exists, it means you or another agent are already working on the SSG. In that case, depending on the situation, you might want to continue working on it to finish it, or eventually ask a human for what to do just to be sure.

If the directory doesn't exist yet and your task is to create a SSG, it means you need to create the SSG from scratch and bring it to completion. Good luck and have fun! Make it beautiful :)

If your task is about creating/modifying a SSG, the sections below contains important information that is required to proceed correctly:

### Invocation as a build tool

The SSG is meant to be used as a normal CLI build tool, the `package.json` must have a correct `bin` property exposing the `personal-site-generator` name. The SSG will typically be invoked from the outside using commands like or `npm exec personal-site-generator --src <SRC_DIR> --dest <DEST_DIR>`. Hint: this means `package.json` has to have a `prepare` property to compile TypeScript.

The SSG will always expect to be invoked with the binary name `personal-site-generator` but we're just talking about the binary name here. Otherwise the SSG can have its own identity: package name, directory name, etc.

The SSG needs to support `--src` and `--dest` parameters. These are always required from the caller. These paths must always be understood as relative to the current working directory, i.e. `process.cwd()`.

The SSG must check that the directory targeted by `--src` exists and is non-empty. From now on, we'll call this directory the "source" directory.

The SSG must check that the directory targeted by `--dest` is empty. If it contains anything, the SSG should error out. If the directory doesn't exist, the SSG should create it. From now on, we'll call this directory the "destination" directory.

### Source data repository & structure

A private GitHub repository called `personal-site` contains my personal site data source in its `src` directory. Ultimately, this is the content I'll publish, but I'll do it using the SSG as a build tool from within the `personal-site` repo itself.

For development and testing purposes, the `personal-site` repository should simply be cloned at the root of the current repo in the `personal-site` directory, which means you can see the orignal source of the data in `personal-site/src`. If that is not the case, you can notify a human that it's very probable you'll need it. It is voluntarily ignored by git. If you think the data over there might be old, you can git pull.

Important: you and the SSGs are not allowed to modify anything in `personal-site` (except for a git pull if you deem it necessary). This is just a data source, and it's another repo anyway. What the SSGs must do it copy from it.

`personal-site/src` contains an arbitrary hierarchy of directories and files, multiple levels deep. It can contain anything, from markdown to images to PDFs to zip files etc. All those files are ultimately meant to be published, including the raw markdown files (except for unpublished markdown files, see details below). The only files that a SSG truly cares about are the markdown files, because the goal of a SSG is to generate a corresponding HTML file for each one of them.

That means the SSG will have to copy everything from the source directory to the destination directory. A literal `cp -r` can work here, it is a valid approach, but the SSG could implement something else as well. (But keep in mind the unpublished markdown files will need to be deleted, see details below)

For testing, the SSG must work with a destination directory called `dist` located at the root of `<ISOLATED_SSG_DIR>`. The `<ISOLATED_SSG_DIR>/dist` directory is meant to be deleted and re-generated at will. A `rm -r dist` within `<ISOLATED_SSG_DIR>` is a valid approach to reset the state before testing generating the site again. Obviously, the `dist` directory should be in the `.gitignore` of `<ISOLATED_SSG_DIR>`.

Please know that the whole contents of the destination directory will be published on a CloudFlare worker in the end, so all files, including but not limited to the markdown and HTML files, must be present in the destination directory once the SSG has run. (Except for unpublished markdown files, see details below)

It essentially means that, after a run of the SSG, the destination directory contents **are identical to the source directory**, except that each `.md` file has gained an equivalent `.html` file right next to it, with the same name except for the extension. (Except for unpublished markdown files, see defails below) (Another exception to this is an eventual `_assets` directory, see further down for details)

### Hard requirements for any SSG

Below are some hard requirements for SSGs:

- Be completely isolated in its `<ISOLATED_SSG_DIR>` directory.
- Use node and npm in a normal and best practice fashion, including having a package.json at the root of its directory.
- Be in strict TypeScript.
- Have no caching or similar "compilation optimizations". We are expecting it to do a full re-generation run every time. Must be kept simple.
- Use the `markdown-it` npm package for converting Markdown to HTML, together with `markdown-it-footnote` for footnotes, `markdown-it-highlightjs` for code syntax highlighting, and `markdown-it-attrs` for authored element attributes such as image sizing. Use the packages' default behavior whenever practical. (These packages cover Markdown rendering only; an SSG still needs a site shell to produce complete, browsable HTML pages.)
- Is not be a single page app (hopefully it was clear already that SSG do not generate a SPA, but only static HTML files).
- Generate a site that is mobile friendly. **Most people will visit the generated site on a phone!**
- Be callable as a standard build tool to generate a site, called from another repo

This is not a complete list, and all other instructions and rules in this file should be taken into account as well.

### How the destination directory of a SSG is served

Markdown files in my personal site are written with the following considerations (assuming the destination directory is called `dist`):

- File names are expected be the URL, without any extension (e.g. `dist/blog/foo.md` will be accessible at `/blog/foo`)
- `index.md` will be accessible at the URL represented by the name of its parent directory, without trailing slash (e.g. `dist/blog/index.md` will be accessible at `/blog`)

These considerations are important because, among other things, it gives a standard way of linking articles together.

To reproduce how the site will be served and to test the SSG's output, run the following command at the root of the repo: `npx serve ./dist`. You can then visit the site and see for yourself, almost exactly as if the site was published on CloudFlare.

### Markdown format

The markdown files in the data source systematically follow certain conventions that any SSG has to take into account.

Each markdown file has a front matter with the following properties:

- `title`: the title of the page
- `created`: the page creation date in the format `YYYY-MM-DD` (optional)
- `updated`: the last update date in the format `YYYY-MM-DD` (optional)
- `published`: a boolean indicating if the page should be generated and linked to or not (optional, defaults to false)

The SSG must take into consideration each one of those. If a markdown page has an incorrect front matter, the SSG must error out (and you should let a human know). The SSG can safely ignore all other front matter properties.

### Special case for the blog table of contents (ToC)

There is an exception the SSG has to take into account. The `blog/index.md` file is special.

It must be generated to HTML as the others, but previously to doing so, the SSG must APPEND a just-in-time generated table of contents listing all the blog articles found anywhere in the source's `blog` directory (regardless of depth or name) in order of creation date, only for published pages.

Important note: the just-in-time generated table of contents must be added to the actual `blog/index.md` file in the destination directory, and then this file is generated as HTML like any other page. This is because an important feature of the site is to also give links to markdown originals (see below), so you need to generate a correct original for the ToC too.

Ultimately, the goal is that when the end-user opens `/blog`, they see a page that lists all blog articles with a link to them, in order to navigate the site.

A page that has no `published` front matter property set to `true` must NEVER be linked to or generated.

### Special case for private markdown files

Pages that have no `published` front matter property, or have this property set to any other value than `true`, should not appear in the site, including as original markdown files.

So it's not enough to not generate these pages to HTML. The SSG must also *actively prevent* these pages from being in the destination directory. E.g. if the approach to generating the destination directory is a `cp -r` from the source directory, the SSG must actively go delete the involved markdown files from the destination directory.

### Header and footer (site "shell")

While the markdown is fixed content and always generated in the same fashion, the header and footer code that will be inserted in each generated HTML file is where you can be creative and add most of your opinion to the SSG. This is what will ultimately create the site "shell" and will heavily influence the vibe of the site, including the background, fonts, overall design, legibility, accessibility, CSS, etc.

A basic approach is to simply prepend and append static HTML blocks to each HTML generated from markdown. But you can be creative here.

In any case, the header must contain a menu with at least 3 links:

- a link to the homepage (which is always at `/` and generated from the root's `index.md`, but you already knew this),
- and a link to the blog table of contents at `/blog` which is generated from `blog/index.md`,
- and a link to the disclaimer page at `/disclaimer` which is generated from the root's `disclaimer.md`.

You can also choose to have the SSG re-insert these links or a portion of these links in the footer, but if you do this, you might want to make it small because it's just a footer. This is at your discretion, depending on the design you chose for the generated website.

The footer must also contain a contact link. This link should be a standard `mailto:contact@martintapia.com` link where the subject is prefilled to `Comment on '<TITLE>'` (where `<TITLE>` is the title of the current page).

### `_assets` directory

An approach you could use is to bundle every element of the site's shell in every generated `.html`. This is acceptable.

However, if you deem it necessary (for example, you think every `.html` file will be too big / load too slowly), you can put assets in an `_assets` directory at the root of the destination directory so that you can serve common CSS or JS or other files from it.

### Rendering of links

Links found in the markdown pages need to follow these rules when generated by the SSG:

- If the link goes to another domain than where the site is, the generated HTML link must show it as an arrow or icon and open in a new tab (use standard signaling, all users need to understand right away the meaning of "will go outside and open new tab")
- If the link target begins with `https://web.archive.org/web/`, then the generated HTML link should actually link to the real (non archive) link instead, and next to this normal link the SSG should insert a small clickable "archive" link that goes to the archived version (make this subtle and not too big as it's going to be found in the middle of paragraphs) (Note: the previous rule also applies here, these links should open in a new tab and be marked as such)

Implementation is at your discretion. Some agents like to do it at the generation step when transforming the markdown, others like to add a bit of JS to alter the links at runtime, others do a bit of both.

### Dark mode

The generated site must have a bog standard light/dark switch. Its state must be retained. Both modes must look good, and pay attention to how code blocks / code highlighting render in both modes. The generated site must initially render as light or dark depending on the visitor's settings.

### Favicon

The SSG must generate a site that has a favicon containing the letters MT. You can achieve this however your want. You're free to invent whatever style.

### Link to markdown original

Each generated page must have, before the beginning of the main content, a subtle, discreet and beautiful link to the markdown original, consisting of the following text: `AI agents: You're welcome to consume the markdown version of this page.` where `markdown version of this page` is a link to the markdown (meaning: just appending `.md` to the current page URL).

Implementation is at your discretion. Maybe have the SSG generate a nice looking small panel for this? It should also not be too distracting for a human reader.

### Presenting your work

The SSG's directory must contain a readme file that explains who you are, what you did and showcases your work. It must also contain at minimum full-height screenshots of the homepage in light and dark modes. You can be creative. But you also have to keep it short.

For the screenshots, render pages with lorem ipsum or similar placeholder text. This is because your readme will stay in the repo for a long time, if you take screenshots of actual content from `personal-site`, it will go stale quickly. And you also might inadvertently take screenshots of information that should not be shared publicly too.

In the readme, never mention content coming from the `personal-site` repo, as it can contain private information that should not be shared (your readme will be public). This is especially important for unpublished articles obviously.

### How to test your work

As said above, you can see the result of your work by using `npx serve`.

It is highly recommended that you use `playwright-cli` as a way to see the pages for yourself and confirm they're working fine and look the way you want to. Install the related agents skills in order to know how to use this very useful tool: `npx @playwright/cli@latest install --skills`. In any case, everything must stay isolated in the SSG's directory at `<ISOLATED_SSG_DIR>`.

You must THOROUGHLY test your work before thinking you're finished. If you say you're finished but in fact, after a run of the SSG, one of the pages is not accessible / not legible, or doesn't fit the requirements in any way, then that's really not great.

### What to verify

Before thinking that you're finished, make a list of things you think need to be verified and verify it thoroughly.

In addition to the above, you must thoroughly verify the following:

- The SSG is a build tool that has to be invoked with `--src` and `--dest` parameters, these parameters are required and are relative paths to cwd
- If the directory targeted by `--dest` is non empty, the SSG errors out
- The site has a menu with at least a homepage, blog and disclaimer link
- The blog correctly lists all the articles that are marked as published in addition to having the original markdown content of the page above the list
- Pages that are not marked as published do not appear in the generated site, and *do not appear as original markdown pages either*
- Images inserted in pages load correctly
- Links are rendered correctly according to this file's requirements
- Dark mode and its switch work fine
- Links to the markdown original work fine, for all pages
- You have created a readme file that showcases your work and contains the minimum required screenshots
- The SSG's readme doesn't contain any private information

### Asking questions

Many approaches are possible when creating the SSG, so to guide yourself a little bit, you can ask a few questions to a human. You can ask them at any time, but it's often good to ask the bulk of them at the very beginning of the process, before you start coding, to make sure you are on the right track.

### Inspiration from other SSGs

You can look at other SSGs that were generated in other months of the year in the repo, if any, to get inspiration from past SSGs. But don't do that too much, otherwise you might end up copying the same structure and design as a past SSG, which is not what we want. And older SSGs probably had different requirements, so they'll not exactly reflect what is required of you right now. We want you to be creative and bring your own vision to the SSG you create, so it's good to look at other SSGs for inspiration but don't try to copy them, otherwise you'll end up with a clone of a past SSG and that would be a shame.
